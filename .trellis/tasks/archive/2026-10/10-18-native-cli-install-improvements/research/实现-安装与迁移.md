# 安装、卸载与显式升级实现证据

## 修改边界

仅修改 scripts/install.sh 与 scripts/test-install.py。沿用单文件 curl 管道安装入口及内嵌 Python 标准库辅助器，不依赖额外远端脚本；不修改 Go、Docker、发行构建、README 或规范。

## 最终行为

- 安装器首次菜单 1 English / 2 中文，回车与无终端默认英文，显式 --lang 跳过；服务凭据及确认继续读取控制终端。
- 新包精确提取两个唯一普通成员 porter、porterd，分别执行 --version 核对；旧 schema1 恢复仍只要求原 porter，普通重跑不升级布局/版本。
- split schema2 包含 layout=split，可选 command_link 固定 /usr/bin/porter。unit 启动 porterd，客户端系统入口使用非强制原子链接；直接安装 /usr/bin 不生成自链接。未知、悬空及同目标未托管链接均拒绝认领或覆盖。
- CLI 配置 /etc/porter/cli.json 采用 schema1、en/zh-CN、root 普通单链接文件0600校验。安装器不预写偏好。普通卸载保留；purge 精确删除已验证配置及 .cli-24位小写hex.new 的受限残留，不递归删除配置目录。
- 显式 --upgrade 下载验证目标双程序包，按 SemVer 比较并拒绝降级。既有 split 同版只校验及修复托管链接，不停服；legacy 同版单程序包仍拒绝迁移。
- 变更前确认、锁后状态及程序/unit/配置快照重校；升级期间原 state.status=upgrading，upgrade_id=upgrade.32位小写hex。

## 持久恢复协议

备份位置 `$INSTALL_DIR/.tmp/upgrade.<32hex>`，权限0700，保留精确原 install.json、程序、unit、porter.env、存在的cli.json与完整data目录。transaction.json严格包含 id、phase、active、enabled、cli、new_link，布尔和阶段值均预先校验。

阶段为 prepared / stopped / backup_complete / switching / restoring / restored。完整备份后才进入 switching；中断时先验证恢复记录，再停服并确认 inactive。未完成备份不会覆盖原数据。替换后失败从完整备份恢复；配置、程序及数据的UID/GID/mode显式保留。恢复数据先构造在DATA父目录 `.porter-restore-upgrade.<id>`，再将失败的新数据目录整体隔离到 `.porter-failed-upgrade.<id>` 后切换完整恢复目录，避免跨文件系统rename和合并新旧数据库。源备份始终保留。

完成恢复后恢复原 active/enabled 意图，最后恢复旧state。成功升级在恢复原服务意图后原子提交 schema2 complete。成功或失败均保留备份供核对，purge明确提示历史备份可能仍有凭据。发现 upgrading 的后续安装/升级/卸载运行优先恢复稳定布局，提示重新执行所需命令。

SIGTERM/INT由shell转发升级子进程，并等待回退完成再释放锁；SIGKILL后的重入依靠持久阶段。

## 安装锁

安装目录与/etc/porter的 `.install-lock` 使用0700目录，安装器写 owner.json `{pid: 正整数, start: /proc/PID/stat开始时间数字字符串}`。未知、缺owner、额外节点、非法metadata、活动owner均拒绝。死owner回收先O_NOFOLLOW打开owner并flock排他锁，再重校目录和owner inode，确认进程身份失效后仅移除该owner与空锁；并发恢复者不得删除新锁。CLI无owner的短暂锁仍保守拒绝。

卸载暂存位于INSTALL_DIR/.tmp/uninstall.XXXXXXXX，不放在全局锁内，以便SIGKILL后回收残锁并续卸载。cleanup受限unlock只删除本进程身份匹配的owner与空锁。
