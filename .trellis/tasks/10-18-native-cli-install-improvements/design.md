# 技术设计

## 1. 双程序与依赖边界

- cmd/porterd 承接现有服务 main/run，保留服务 version 注入、信号、HTTP、规则和本机控制生命周期；移除对 internal/cli 的引用。解析参数后才能加载服务配置，未知参数不能启动服务。
- cmd/porter 只处理客户端信号、version 及 cli.Run。无参数转换为 rules 入口，既有 porter rules 命令不变；--version/-version 先返回版本。CLI 不嵌入 Web、不引用配置/存储/转发/规则服务。
- 当前 internal/localapi 同包同时定义 Client 和引用 rules.Service 的 Server，直接拆 main 不足以隔离依赖。新增 internal/controlapi（命名可在实现中按现有约定微调）承载共用请求/响应、错误、Client 和 revision 协议解析；internal/localapi 仅保留服务端，依赖 controlapi 及 rules。
- CLI 使用 controlapi；服务使用 localapi。共用 model 不复制校验；服务仍以 rules.Service 为唯一业务入口。整理测试以跟随责任归属，避免公共协议反向依赖实现。
- 本机 socket 默认与覆盖路径、真实 UID0 SO_PEERCRED、可信目录、0600、revision 和关闭等待合同保持。原生程序仍识别容器环境并禁用控制。

## 2. Docker 与发行

Dockerfile 仅编译 cmd/porterd，保持 porter_docker 标签，最终只复制 /porterd 并更新 ENTRYPOINT。服务端 linux 实现可用 !porter_docker 标签与 Docker stub 隔离，本机控制监听在 Docker 构建不可启用；不以环境变量重新打开。镜像不复制 CLI，不承诺未经测量的体积收益。

build-release.sh 为 amd64/arm64 各构建 porter、porterd，二者同一 VERSION 注入，归档保留 porter-VERSION-linux-ARCH.tar.gz 及两个 README。使用干净的受控暂存目录，明确归档成员，避免复用残留产物。归档摘要校验不变；安装解包只提取精确的普通文件，拒绝重复成员、链接、错误版本和缺少任一程序。

CI 添加两个入口及依赖边界检查，Docker smoke 改为验证不存在客户端、porterd 不接受规则命令、默认/自定义控制 socket 不存在，保留完整业务回归。

## 3. 安装语言与布局

安装器 LANGUAGE=en，菜单 1 English/2 中文，空/1/en 为英文，2/zh-CN 为中文；显式语言预扫描及无终端帮助继续可用。新升级提示同样进入双语字典。CLI 首次选择采用相同编号和默认值，但独立保存，安装器不预写 CLI 偏好。

双程序布局：SERVER=$INSTALL_DIR/porterd，CLIENT=$INSTALL_DIR/porter，COMMAND=/usr/bin/porter。unit 仍为 porter.service，仅 ExecStart 指向 SERVER，服务用户、限制、配置与数据库位置不变。COMMAND 使用绝对链接；CLIENT==COMMAND 时直接托管普通客户端文件，不写链接归属。

COMMAND 及父目录按系统实际路径校验，支持 usr-merge 的合法系统布局但不接受用户可写或未知链接重定向；具体沿用既有安装器路径保护，不能为便利而关闭整体检查。测试所有生产路径映射到仓库 .tmp。

### 3.1 CLI 语言配置

固定 /etc/porter/cli.json，内容为 schema=1、language=en或zh-CN 的小型 JSON。与 porter.env（服务凭据）和 install.json（安装归属）分别管理；客户端只依赖本地文件，服务端和业务数据库不读取 CLI 偏好。采用系统范围是因为该工具仅root/sudo可管理规则，避免HOME/sudo环境造成两套偏好。

语言解析顺序：先预扫描显式 --lang；有值仅本次使用且不保存。否则读取合法偏好；缺省时在控制终端首次选择1English/2中文、回车英文。确认后保存再继续原命令。取消/EOF/中断不保存。无终端且无偏好须明确要求 --lang；已有偏好则参数方式无需额外交互。版本查询完全跳过配置。交互菜单提供语言切换，确认后更新当前界面和保存值；不新增数据库设置或用户/套餐命令。

系统文件写入仅限原生root；help等非root只读路径不得创建配置，无法读取系统偏好时可用显式语言，无显式值则在终端选择仅本次使用并提示不保存。容器不写系统配置。非root管理命令仍按既有权限错误退出，不能因选择语言获得权限。文件缺失与文件损坏区分：损坏/未知schema/非法语言给出可见诊断，不静默覆盖；用户可用 --lang 完成本次操作并按提示修复配置。

目录必须可信、root所有且非其他用户可写；文件是root所有的普通非链接文件，模式0600。限制读入大小，拒绝符号链接、悬空链接、目录和不可信属主；不source任何配置。写入使用受限同目录临时普通文件与原子替换，采用受限配置锁串行化，首次并发创建在锁内重读已有值，避免未确认覆盖。CLI配置锁与安装器协调，不持锁等待用户输入，也不因卸载目录移除而重建已开始卸载的托管安装；测试并发保存/卸载，不删除他人新文件。配置临时文件只在其配置目录，开发验证仅仓库.tmp。

语言保存失败以所选语言发出明确警告，当前交互继续使用所选值，下次可能重新选择；不得在JSON标准输出混入提示。固定配置文件不承载秘密，但仍以0600统一限制修改来源；客户端依赖边界检查保持不引用配置/数据库服务包。

## 4. 安装记录与入口归属

新布局使用 schema=2、layout=split、directory、arch、version、status，command_link 可选且只允许固定 /usr/bin/porter。旧 schema=1 解读为 legacy 布局，无 command_link；不将未知手动链接认领为本安装所有。旧安装器应拒绝 schema=2，避免把客户端作为服务启动。

schema=2 保留 initializing/complete/uninstalling/uninstalled，并有专用升级中状态及恢复信息。所有路径从验证后的目录和固定常量推导，状态不能指定任意待删除文件；字段类型、版本与合法状态组合严格校验。

链接使用既有两把锁，冲突预检后先原子记录固定管理意图，再非强制 ln -s 原子创建。已声明且缺失可修复；已声明且类型/属主/目标匹配可接受；其他一律拒绝。不能使用 ln -sf、不能只用 test -e 忽略悬空链接。锁内重校状态和节点，意图与创建之间失败允许安全重试。

complete 的程序/配置/unit/数据缺失保护保持；仅缺少已声明的外部命令链接可补齐。uninstalled 恢复下载原版本与原布局，不自动换最新；双程序缺一不得用下载覆盖掩盖完整状态损坏。

## 5. 旧安装保留及显式升级

普通重跑按记录保留版本和布局：schema=1 仍运行旧 porter 服务，不更名、不写 CLI PATH 链接；输出实际版本、布局和显式升级方法。旧单程序发行包恢复仍走精确 porter 普通文件校验。无需运行 rules 探测旧服务程序，避免加载配置或意外启动第二服务。

--upgrade 可配 --version，目标必须双程序且不得低于当前版本；预发行版本比较须按 SemVer 规则，不能字典排序。不指定版本使用最新正式 Release；卸载不能组合 upgrade/version，未托管实例拒绝 upgrade。同版本已拆分完整安装只做幂等检查/托管入口补齐，不重启。目标等于旧单程序版本但归档仍是单程序时明确拒绝，不重写已发布资产。

升级状态机：

1. 只读预检当前状态、真实程序版本、原始 unit 模板、账号、DB/配置及所有目标；拒绝未知 porterd/COMMAND、自定义 drop-in 或变更的 unit。目标包在暂存中下载/摘要/双版本校验，失败不停止现有服务。升级预检及锁内重检DATA自身不是挂载根：解析/proc/self/mountinfo并解码路径转义，包含同fs bind mount；不能只用ismount或st_dev。整体目录恢复依赖rename，DATA自身挂载根会EBUSY，应停服前拒绝；父目录/var单独文件系统仍可用。
2. 显示源/目标与停机/备份范围，终端确认。获得两把锁后重新校验全部快照；取消不更改托管资源。先保存原始状态文件的精确快照，再记录受限的升级意图和原布局、原版本、目标版本、原 active/enabled 状态；备份的旧状态不能是已覆盖的升级中记录。
3. 停止原服务并确认 inactive；在安装目录 .tmp 中建立权限0700的持久升级工作目录，保存原程序/原unit/原state、配置（含已存在的CLI偏好）及完整数据目录备份，文件归档0600。备份完成标记须原子提交；数据不完整时不能进入替换阶段，原程序仍可重启。
4. 备份完整后写持久阶段标记，再用受限 .new+rename 安装双程序、unit 与托管入口，daemon-reload。启动并检测新版本、运行状态与健康；验证后恢复原 active/enabled 意图（原本停止的实例仅临时启动验收，随后停止），再原子提交 schema=2 complete。服务名和凭据不改变。
5. 失败/信号回滚：根据持久阶段恢复原程序/unit/状态以及匹配的完整配置数据；保留 UID/GID、模式、内容及原 active/enabled 状态。恢复完整目录前确认新服务已停止，不能把新旧数据库文件合并。入口仅清理本轮声明且匹配的节点。
6. 强制中断后的下次运行先识别升级记录，按阶段恢复原稳定布局；不能依据二进制文件名猜测已完成。备份未完成的阶段不拿半备份覆盖数据；备份已完成可恢复后重试。回滚失败则保留记录/备份并明确人工恢复位置，禁止继续安装或卸载。

工作目录必须由受限记录和固定目录规则验证归属，拒绝链接或替换节点；正常 cleanup 不删除仍需要恢复的升级备份。稳定完成后才清理可确认属于本次操作的暂存；保留至少本次回退备份及明确位置/版本，不自动清理未知历史备份。记录中仅存受限标识，不信任任意绝对恢复/删除路径。

这是对旧规划“不新增升级”的有意扩展，原因是程序名称和 unit 切换必须成为一个明确的可恢复动作；该范围已在最终方案中展示并获用户批准。

## 6. 卸载与回退

新旧布局按相应记录生成预期 unit。停服前验证程序、unit、账号及托管链接，未知替换拒绝；确认后精确移除该布局的程序、unit、声明的 COMMAND 及受限 .new。普通卸载保留原布局/版本/入口管理意图及 CLI 配置以便恢复。purge 明确删除 /etc/porter/porter.env、/etc/porter/cli.json、install.json 及可确认归属的未提交配置文件；停服前预检类型/属主，未知链接或替换目录拒绝，不递归删除整个/etc/porter。purge 不删除未知文件或历史升级备份、DATA父目录中的失败新版数据隔离副本，提示与文档说明实际位置及可能含凭据/业务数据；空目录仅用rmdir移除。

升级中先恢复稳定布局再卸载。旧 record 不管理的 COMMAND 不删除。手工安装和定制 unit 仅给出迁移文档，不替用户接管；Docker 外部硬编码 /porter 须按新的 /porterd 更新，不额外保留含 CLI 的兼容二进制。

不对生产数据库做拆分专属迁移。回退任何已运行目标版本须使用与旧程序匹配的完整配置数据备份，不能仅恢复旧可执行文件。部署脚本、业务数据库与安装状态 schema 分别处理。

## 7. 验证边界

安装器模拟测试覆盖全部生产路径重写、旧/新包、状态与故障阶段；真实程序/PTY验证进程边界和 PATH。可信隔离环境验证真实 root/nonroot socket 权限，不增加生产例外。两架构交叉编译不等同 arm64 实机运行；非 systemd PID1 环境仅报告静态 unit 和替身测试。Docker 按最终镜像完整 smoke，构建工具差异仅在 .tmp 验证副本处理。

## 实施补充：强制中断残锁

升级恢复需能取得SIGKILL后遗留的已确认安装器锁。新安装器为目录锁写入受限owner.json（pid与proc starttime），仅回收确认已死且inode不变的安装器锁；使用owner fd的flock与目录/文件inode重校防多个恢复者误删新锁。无owner的CLI短锁仍作为未知锁保守拒绝，锁协议不能放宽到自动清理任意空目录。具体实际合同见backend/native-install-contracts.md第10.8节。
